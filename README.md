# 前端布局设计规范 · Frontend Layout Design Spec

一套可直接照做的**前端布局与交互规范**，用于把界面做「稳」：间距、圆角、投影、字体层级、响应式断点、常见版式、动效、对比度与无障碍，每一项都给出可检查的阈值，而不是「留白要合理」这类无法执行的描述。

## 这份规范解决什么问题

多数界面不是「不会做」，而是**每次做都在重新决定**：这个卡片内边距用 16 还是 20？这个弹层圆角跟谁对齐？禁用态到底该降透明度还是换底色？决策成本高、结果不一致，几屏之后就开始发散。

这份规范把这些决定**一次性收敛成令牌和规则**，并给出每条规则背后的原因与「违反后的具体症状」——症状比规则更容易在评审时被发现。

## 怎么用

**人工评审**：§10 的清单逐项过一遍，比通读全文更快。

**自动检查**：§9.1 给了可直接运行的 grep 命令，覆盖 `transition: all`、`0fr` 高度动画、滚动元素误用 `h-full`、禁用态降透明度、渐变文字等高频违规。命中不等于错误，需人工判断。

**作为 Agent 规范**：把 `LAYOUT_SPEC.md` 放进项目的规范目录或装成本地 skill，让编码 Agent 在动手前先读它。

## 与具体品牌的关系

规范里的**原则与阈值是通用的**；色值、字体族、模块配色属于**实例令牌**，可整体替换。

判断一条规则是否属于「可迁移原则」的方法是：把颜色全部换成灰度、字体全部换成同一族，这条规则还成立吗？
- 成立 → 是原则（例如「相邻嵌套表面的亮度差 ≥ 0.04」）；
- 不成立 → 是主题选择（例如「画布用暖白不用冷灰」）。

附录 A 说明了本规范从两份来源材料（一份主流 AI 产品官网的公开设计规范、一份私有工具型产品的设计语言）中各自采纳与舍弃了什么，以及冲突处如何取舍。

## 使用与授权

MIT。可直接复制进自己的项目规范目录，改写色值与字体族即可。

欢迎提 Issue 讨论阈值是否合理——**任何无法在评审现场被判定「违规/不违规」的规则，都应该被改写成可以判定的**。
